# 1. Why NOT Store Files in Database?

Suppose a user uploads:

- Profile Photo = 5 MB
    
- Video = 100 MB
    
- PDF = 20 MB
    

If you store these inside MySQL/Postgres:

```sql
User
-----------------------------------
id
name
photo_blob
video_blob
pdf_blob
```

Problems:

### Storage Explosion

Imagine:

```text
1 Million users
100 MB average upload

= 100 TB data
```

Databases are expensive for huge binary files.

### Slow Queries

When fetching:

```sql
SELECT * FROM USER
```

Database may need to deal with massive BLOB columns.

### Backup Nightmare

Backing up:

```text
10 GB DB → easy
10 TB DB → painful
```

### Replication Cost

Primary DB → Replica DB

All binary data gets replicated.

Huge network cost.

# 2. Why S3?

Amazon S3 is **Object Storage**. ([AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/?utm_source=chatgpt.com "What is Amazon S3? - Amazon Simple Storage Service"))

It is designed for:

- Images
    
- Videos
    
- PDFs
    
- Audio
    
- Logs
    
- Backups
    

Example:

```text
Bucket: instagram-media

Objects:

user1/photo.jpg
user1/video.mp4
user2/resume.pdf
```

S3 handles:

- Durability
    
- Replication
    
- Scaling
    
- Versioning
    
- Encryption
    

without stressing your database. ([AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/?utm_source=chatgpt.com "What is Amazon S3? - Amazon Simple Storage Service"))

# 3. Database vs Blob Storage

|Database|Blob/Object Storage|
|---|---|
|Structured Data|Unstructured Files|
|Fast Queries|Massive File Storage|
|Expensive|Cheap|
|ACID Transactions|File Operations|
|MBs/GBs|TBs/PBs|
|User Data|Images/Videos|

Example:

### Database

```sql
User
-----
id
name
email
photo_url
```

### S3

```text
bucket/photos/user1.jpg
bucket/photos/user2.jpg
```

Database stores:

```sql
photo_url
```

only.

Actual file lives in S3.

This pattern is called:

**Pointer Pattern**

```text
DB ---> S3 Object
```

and is industry standard. ([arXiv](https://arxiv.org/abs/2512.06852?utm_source=chatgpt.com "A Chunked-Object Pattern for Multi-Region Large Payload Storage in Managed NoSQL Databases"))

# 4. What is Metadata?

Metadata = Data about Data.

Suppose:

```text
File = cat.jpg
```

Actual Data:

```text
Binary Image
```

Metadata:

```json
{
  "fileName":"cat.jpg",
  "size":"2MB",
  "uploadedBy":"123",
  "contentType":"image/jpeg",
  "createdAt":"2026-08-10"
}
```

S3 automatically stores system metadata such as:

- Size
    
- Creation Time
    
- Content Type
    
- Storage Class
    

and also supports custom metadata. ([Amazon Web Services, Inc.](https://aws.amazon.com/s3/features/metadata/?utm_source=chatgpt.com "Data Discovery Accelerator - Amazon S3 Metadata - AWS"))

# 6. What is a Pre-Signed URL?

A Pre-Signed URL is a temporary URL generated by backend that allows upload/download of a specific S3 object without exposing AWS credentials. ([AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html?utm_source=chatgpt.com "Download and upload objects with presigned URLs - Amazon Simple Storage Service"))

Example:

```text
https://s3.amazonaws.com/...
?X-Amz-Signature=abc123
&Expires=3600
```

Valid for:

```text
1 hour
```

After expiry:

```text
403 Forbidden
```

# 7. Why Not Upload Through Backend?

Bad approach:

```text
Client
   |
100 MB File
   |
Backend
   |
100 MB File
   |
S3
```

Backend becomes bottleneck.

For 1000 users:

```text
1000 × 100 MB

= 100 GB traffic
```

through your servers.

Cost ↑

Latency ↑

CPU ↑

Memory ↑

---

# 8. Better Approach: Pre-Signed URL

### Step 1

Client asks:

```http
POST /upload-request
```

### Step 2

Backend generates:

```java
preSignedUrl
```

### Step 3

Backend returns:

```json
{
  "uploadUrl":"..."
}
```

### Step 4

Client uploads directly to S3

```text
Client -----> S3
```

Backend never touches the file. ([AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/PresignedUrlUploadObject.html?utm_source=chatgpt.com "Uploading objects with presigned URLs - Amazon Simple Storage Service"))

# 11. Interview Question

**Q: Why use Pre-Signed URL instead of uploading through Spring Boot API?**

Answer:

1. Reduces backend load
    
2. Saves bandwidth
    
3. Better scalability
    
4. Faster uploads
    
5. No AWS credentials exposed
    
6. Time-limited secure access
    
7. Works well for large files (videos/images) ([AWS Documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html?utm_source=chatgpt.com "Download and upload objects with presigned URLs - Amazon Simple Storage Service"))
